# 开工设计说明

日期为2026-11-26。本文件由AI按A产品、B编排、C数据、D测试四种职责起草，状态为待团队确认。方案沿用需求V1.1。

## 第一周交付

创建三日旅行 → 添加两个景点 → 排序 → 保存 → 刷新恢复。
跨天、时间计算、预算和路线联动在第二轮验收。第一周提供这些区域的占位与一致数据结构。

## A与B的页面草图

### 旅行列表页

~~~text
旅行行程规划                            [+ 创建旅行]
┌─────────────────────────────────────────────────┐
│ 杭州三日游 · 2026-12-01至12-03                   │
│ 最近更新……                         [打开][删除] │
└─────────────────────────────────────────────────┘
空态：创建你的第一份旅行 [+ 创建旅行]
~~~

创建弹窗填名称、开始日期、2–5天和预算金额。金额页面用元，提交转换为整数分。名称去除首尾空白后1–50字。非法字段就地提示。创建成功跳转编辑页。请求进行中禁用重复提交；结果未知时先刷新列表核对。

### 行程编辑页

~~~text
[返回] 杭州三日游   [编辑基本信息]   保存状态 [立即保存]
┌──────────────┬─────────────────────────┬──────────────┐
│ 景点         │ [第1天][第2天][第3天]    │ 路线示意     │
│ 搜索、分类   │ 起止09:00–21:00          │ ① → ②        │
│ 景点A        │ ① 景点A 停留60分钟       ├──────────────┤
│ [详情][加入] │ [上移][下移][移到][删除] │ 预算与费用   │
│ 景点B        │ ② 景点B 时间及冲突提示   │ 门票、交通   │
│ [详情][加入] │ 空日提示添加景点          │ 其他、总计   │
└──────────────┴─────────────────────────┴──────────────┘
~~~

加入指当前选中日。重复加入显示原因，跨天重复则恢复原位置。按钮排序与拖动使用同一操作函数。日期切换保留未保存编辑。第一轮先实现按钮调整，拖动在容量允许时接入。

保存显示未保存、保存中、已保存、失败或版本冲突。失败保留草案并可重试，过期响应不能清空新编辑。删除和缩短天数前确认影响。

## C的模块图

~~~mermaid
flowchart TD
 A[景点与旅行入口] --> S[共享旅行草案]
 B[每日行程编辑] --> S
 S --> T[时间预算计算]
 S --> M[路线示意]
 T --> V[时间与预算展示]
 S --> Q[串行保存队列]
 Q --> API[HTTP接口与校验]
 API --> DB[(SQLite事务与版本)]
~~~

前端共享状态维护原始输入，派生结果由统一函数计算。保存请求携带baseRevision，服务端事务比较并更新revision。返回成功时若仍有新草案，继续保存新快照。

## C与D的数据关系


同日景点唯一，行程项id稳定，order从0连续。参考交通有方向，缺失时间和费用分别处理。金额为整数分；分钟0表示00:00。完整样例见 trip-example.json。正式字段、限制以需求V1.1为准。

## 待确认的技术方案

建议Vue 3 + TypeScript + FastAPI + SQLite，后端规则使用pytest，端到端使用Playwright。这个组合用于说明模块边界，真实组员需确认熟悉程度再决定。接口契约保持与框架无关。

## 开发交接

A接景点样例，调用加入当前日操作；B维护行程操作入口；C给出共享数据、接口和计算；D用同一数据画路线并核对结果。第一轮先联合跑通创建、添加、保存、刷新，再增加排序。
